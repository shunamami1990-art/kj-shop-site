# 通用约定（所有契约共用）

版本：0.16.1

## 1. 编码与格式

- HTTP + JSON，UTF-8；请求和响应的 `Content-Type` 为 `application/json`，站点回复通知时除外（见 C1）。
- 字段名使用小驼峰。
- 时间为 RFC 3339 格式的 UTC 时间，如 `2026-10-13T08:00:00Z`。

## 2. 金额

- 接口中的金额一律为字符串小数，不使用 JSON 数字。
- 小数位数固定，由币种决定：

| 币种 | 代码 | 小数位 | 示例 |
| --- | --- | --- | --- |
| 人民币 | `CNY` | 2 | `"60.00"` |
| USDT（TRC20） | `USDT` | 6 | `"8.300000"` |

- 小数位数不符的金额视为参数错误，不做四舍五入。
- 整数部分最多 12 位。这样换算成最小单位后不会超出数据库 64 位整数的范围。
- 比例为字符串小数，表示占比，最多 6 位小数，如 `"0.006000"` 表示 0.6%。

## 3. 签名（机器间调用）

请求头：

| 请求头 | 含义 |
| --- | --- |
| `X-KJ-Key-Id` | 密钥编号；站点调用时为站点编号 |
| `X-KJ-Timestamp` | Unix 毫秒时间戳 |
| `X-KJ-Nonce` | 随机串，16–64 个字母或数字 |
| `X-KJ-Signature` | 签名，小写十六进制 |

请求的待签字符串（第一行是固定的文字 `KJ-REQ`）：

```
KJ-REQ \n 请求方法 \n 路径（含查询串） \n 时间戳 \n 随机串 \n 请求体原文
```

- 请求方法为大写，如 `POST`；路径不含域名，如 `/v1/orders`。
- 请求体原文是实际发送的字节，不做任何格式化；没有请求体时为空字符串。
- 签名 = HMAC-SHA256(密钥, 待签字符串)，输出小写十六进制。
- 接收方拒绝：时间戳与本机时间相差超过 5 分钟；同一密钥下 10 分钟内重复的随机串；签名不符。服务多实例运行时，随机串的记录必须在各实例之间共享。

响应同样签名，响应头带同样四项（时间戳、随机串由响应方新生成），待签字符串（第一行是固定的文字 `KJ-RESP`）：

```
KJ-RESP \n 请求方法 \n 路径（含查询串） \n 时间戳 \n 随机串 \n 请求的随机串 \n 响应体原文
```

- "请求方法""路径""请求的随机串"取这次请求的值，所以一条响应只对它所回答的那一次请求有效，不能拿去回答另一次请求；第一行使请求和响应的签名不能互相冒充。
- 调用方用自己发出的随机串验证响应签名；签名不符时按调用失败处理，不使用响应内容。调用方不需要检查响应的时间戳和随机串是否重复。
- 请求验签失败（时间戳超出范围、随机串重复、签名不符、密钥编号不存在）时，返回的错误响应不签名。
- 例外：站点回复 core 的通知时只回复 `success` 原文，不签名（C1）。
- 签名覆盖的是服务实际收到的路径；反向代理不得改写路径。
- 标准用例：`testdata/signature-cases.json`。

服务间密钥按"调用方、提供方"一对一分配：同一个调用方对不同的提供方使用不同的密钥，密钥编号仍为调用方的名称（如 `core`）。提供方只保存自己的各个调用方的密钥。这样任何一个服务被攻破，只能冒充它自己。

密钥轮换（0.10.0，M7 草案第 1.2 节）：提供方的 `KJ_INBOUND_KEYS` 允许同一个密钥编号有两把密钥（最多 2 把）——JSON 格式的服务写成数组（`{"core":["新","旧"]}`），`编号:密钥,...` 列表格式的服务（channel-usdt、usdt-signer）允许同一编号出现两次（`core:新,core:旧`）。任一把验签通过即可，响应用通过的那把签名；两把都试完再返回 401；随机串记录按 `(密钥编号, 随机串)`，与密钥值无关；验签日志（不含值）记用的是第几把（`keyIndex`）。调用方的 `KJ_OUTBOUND_KEYS` 仍为单值。例行切换：提供方加新保留旧 → 调用方换新 → 核对 24 小时内没有旧把的请求 → 提供方删旧；密钥泄露时提供方直接替换（不并存），调用方同时换新。

core 调用站点（通知、校验客户账号）时，`X-KJ-Key-Id` 为站点编号，密钥为该站点的接口密钥。

具体的密钥编号见各项目的设计文档。

## 4. 响应结构

```json
{ "code": "OK", "message": "", "data": {} }
```

- 成功时 HTTP 状态码为 200，`code` 为 `OK`。
- 失败时 HTTP 状态码按下表，`code` 为具体错误码，`message` 为便于排查的说明。

### 4.1 可选字段

契约里不是必填的字段，没有值时可以省略，也可以为 `null`；调用方两种都要接受，不能依赖其中一种。

## 5. 通用错误码

| code | HTTP | 含义 |
| --- | --- | --- |
| `OK` | 200 | 成功 |
| `INVALID_PARAM` | 400 | 参数缺失或格式错误；`message` 指出字段 |
| `UNAUTHORIZED` | 401 | 签名或令牌无效、过期、随机串重复 |
| `FORBIDDEN` | 403 | 该角色无权执行这类操作 |
| `NOT_FOUND` | 404 | 对象不存在，或不在调用方的数据范围内 |
| `CONFLICT` | 409 | 与已有数据冲突，如同一订单号参数不同 |
| `RATE_LIMITED` | 429 | 调用过于频繁 |
| `INTERNAL_ERROR` | 500 | 服务内部错误，可以重试 |
| `NOT_IMPLEMENTED` | 501 | 该接口在当前阶段还没有提供（如骨架阶段范围以外的接口）；签名、调用方等检查照常先做，通过后才返回这个码。调用方不要重试，按"功能未提供"处理 |
| `UNAVAILABLE` | 503 | 依赖的服务暂不可用，可以重试 |

各契约另有自己的业务错误码。

## 6. 幂等

- 所有"创建"类接口都由调用方提供唯一编号（如站点订单号、退款编号、事件编号）。
- 同一编号、同样参数重复调用，返回与第一次相同的结果，不重复创建。
- 同一编号、不同参数，返回 `CONFLICT`。

## 7. 重试

- 调用方遇到网络错误、`INTERNAL_ERROR`、`UNAVAILABLE` 时可以用同一编号重试。
- `core` 通知站点：间隔为 0、30、60、300、600、1800、3600 秒，共 7 次；全部失败后告警，由人工补发。`core` 调用站点（通知、校验客户账号）等待回复最多 15 秒（连接 5 秒）；不同事件的通知各自独立发送，不保证到达顺序（0.15.3 写明，实现未变）。
- 通道向 `core` 推事件：见 C3。

## 8. 平台与数据范围

平台编号（`platformId`）：总平台固定为 `root`；子平台由 `org` 生成，如 `P01`，生成后不变。

每个接口操作在 OpenAPI 中用 `x-kj-scope` 标注谁可以调用，取值为下表中的一个或多个。缺少标注时全量验证不通过。

| 取值 | 调用方 | 数据范围怎么确定 |
| --- | --- | --- |
| `public` | 任何人，不需要身份 | 不涉及平台数据 |
| `site` | 站点的程序，用站点接口密钥签名 | 本站点：只能访问这个站点自己的订单和退款 |
| `channel` | 通道项目，用服务间密钥签名 | 请求中的通道账户编号所属的子平台 |
| `internal` | 其他内部服务，用服务间密钥签名 | 见各接口说明 |
| `root` | 总平台的账号 | 总平台自己的数据；查看子平台数据时用下面的请求头选择 |
| `platform` | 子平台的平台账号 | 令牌里的所属平台 |
| `merchant` | 商户账号 | 令牌里的所属平台和商户 |
| `agent` | 代理账号 | 令牌里的所属平台和代理 |

规则：

- 使用令牌的接口，数据范围只取自令牌（C7），不取自请求中的任何参数。
- 总平台的账号用请求头 `X-KJ-Platform: <子平台编号>` 选择要查看的子平台；其他账号带这个请求头时忽略。总平台的账号在子平台范围内只能查看；只有超级管理员可以操作（例外：总平台财务可以撤销超级管理员的等待生效操作，C4）。
- 按编号访问不在自己数据范围内的对象，一律返回 `NOT_FOUND`，不返回 `FORBIDDEN`，不透露对象是否存在。
- 请求体字段引用不在自己数据范围内的对象时（0.6.7 起写明），结果与该对象不存在时完全相同：接口说明为这个字段规定了错误码的按其规定（如 `INVALID_PARAM`、`FORBIDDEN`），没有规定的为 `NOT_FOUND`。无论哪种，"不存在"和"不在范围内"必须返回同样的码和同样的 `message`。
- 列表接口的筛选条件（如 `partyId`、`siteId`）指向数据范围外的对象时，返回空列表，不报错。
- `FORBIDDEN` 只用于"这个角色不能做这类操作"。
- 总平台自己的操作（如确认系统使用费"已收"）不属于"在子平台范围内的操作"：涉及哪个子平台写在路径里，不使用 `X-KJ-Platform` 请求头，由总平台的相应角色直接完成。哪些接口属于这一类，在各契约中逐个标明。

带令牌的接口（`x-kj-scope` 含 `root`、`platform`、`merchant`、`agent`）另有两个标注（0.6.0 起），缺少时全量验证不通过。集成测试据此自动生成隔离用例：

- `x-kj-roles`：写在接口操作上，列出可以调用的角色（C7 第 2 节的标识），不在其中的角色调用返回 `FORBIDDEN` 或 `NOT_FOUND`。超级管理员不列出（按 C7 第 4 节和各契约的说明）；`x-kj-roles: []` 表示只有超级管理员可以调用，此时 `x-kj-scope` 为 `[root]`（0.17.0）。读接口列出 `root_admin`、`root_finance` 表示可以查看；写接口列出它们表示该角色可以调用（总平台自己的操作、本人的操作，或契约写明的例外，如撤销等待生效操作、账本检查），集成测试的"总平台账号带 `X-KJ-Platform` 写入应被拒绝"检查跳过这些接口；没有列出总平台角色的写接口，总平台账号带 `X-KJ-Platform` 调用时只有超级管理员可以写。契约另行写明的有条件放开（如 C4 的客服可见范围）不列出。
- `x-kj-ref`：写在路径参数、查询参数和请求体字段上，标出这个值引用哪类对象。名字以 `Id`、`Ids`、`No` 结尾的（`requestNo` 除外）都必须标注。取值：`platform`、`merchant`、`site`、`agent`、`user`、`channel_account`、`fund_account`、`payee_account`、`order`、`receipt`、`refund`、`notification`、`manual_payment`、`fund_transfer`、`withdrawal`、`adjustment`、`system_fee_settlement`、`system_fee_refund`、`delayed_operation`、`shop_order`、`alert_record`、`channel_settlement`、`recon_diff`（后两个 0.8.0）、`shop`、`shop_code`、`allocation`、`prepaid_topup`（0.14.0，C4 店铺码通道与预付款）；`party` 表示类型由同一请求里的 `ownerType`、`partyType`、`providerType`（0.16.0）、`ptype` 或 `groupBy`（0.8.0）决定，没有这类字段时由编号的格式决定（第 12 节）；`ownerType` 为 `prepaid`（0.14.0，C4 提供方预付账户）时 `ownerId` 为提供方编号，类型按第 12 节的编号格式决定（`M…` 商户、`AG…` 代理，0.16.0；此前按 `merchant` 处理）；`none` 表示不是对已有对象的引用（如调用方新生成的编号、外部系统的单号）。

## 9. 向外部地址发起的调用

站点的通知地址、校验客户账号地址、合作商的接口地址由使用者填写。保存和调用时都要检查（保存时检查 `https` 和主机：`localhost`、内部网络、本机或保留地址的 IP 字面量直接拒绝，不解析域名；解析域名后的检查在每次连接时由发起调用的一方做）：

- 必须是 `https`。
- 端口只能不写或写 `443`（0.12.5）：正式环境的容器出站只放行 tcp 443，别的端口连不通。保存站点地址（org）、登记合作商接口地址（core）、下单带 `notifyUrl`（C1）时写了别的端口都返回 `INVALID_PARAM`，`message` 写明"端口只能是 443"。
- 解析出的地址不得是内部网络、本机或保留地址。
- 不跟随重定向。
- 先解析域名、检查解析出的地址，再直接连接这个已检查过的地址，防止解析结果在检查之后被换掉。

只有本机开发环境可以用开发开关 `KJ_DEV_ALLOW_INSECURE_URLS` 放宽为允许 `http` 和本机、内部网络地址（第 11 节）。

## 10. 实现时必须遵守的前提

- 反向代理删除外部请求自带的 `X-KJ-Host`，再写入真实访问的域名；后端端口只对反向代理开放。
- 后端收到的请求没有 `X-KJ-Host`，或者其中的域名没有登记（既不是总平台域名，也不是任何子平台绑定的域名）时，在任何环境都**不得**按总平台域名处理：登录和刷新令牌返回与"账号或密码错误"相同的结果（C7 第 5 节），站点接口返回 `UNAUTHORIZED`（C1）。本机开发和集成测试经反向代理访问，或者直接调用后端时自己带上这个请求头。
- 反向代理同样删除外部请求自带的 `X-KJ-Client-IP`，再写入真实的客户端地址。后端记录操作日志、登录日志里的 `ip` 时取这个请求头；没有这个请求头时（本机开发、服务之间的调用）取连接的对端地址。不读取 `X-Forwarded-For` 等可以由外部伪造的请求头。
- 使用数据库行级安全的服务：每个事务都必须设置当前平台，没有设置时一律查不到数据、写不进数据；设置必须与连接池里的那个事务绑定，不能残留到下一个请求。
- JWT 库必须检查头部的 `typ` 和算法。
- 子平台、商户、代理录入的名称等文字，在任何后台页面（尤其总平台的页面）中都要转义后显示。
- 动态码校验、审核声明签发、登录都要限制尝试次数。
- 告警的标题使用固定模板，不直接拼接外部输入的文字。
- 幂等编号（站点订单号、退款编号等）按站点或平台分别判重，`CONFLICT` 不能透露别的平台是否用过这个编号。

- 店铺码付款页（0.14.0，C4"店铺码通道与预付款"）：反向代理把 `/pay/` 转给 core 的站点接口端口（18010），这条路由写在兜底的 `/` 之前；CSP 为 `default-src 'none'; img-src 'self'; style-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`；`/pay/` 单独一个按客户端 IP 的计数（每 IP 每分钟 120 次，超过 429），不与其他路径共用额度；从备份恢复后的"只开后台"状态下 `/pay/` 与 `/v1/` 一样返回 503；访问日志里 `/pay/` 之后的令牌段打码。付款页只在子平台绑定的域名上有效（core 按 `X-KJ-Host` 判断，总平台域名上一律 404）。core 新增保密变量 `KJ_PAY_TOKEN_KEY`（32 字节随机值的十六进制，付款页令牌的 HMAC 密钥；更换后已发出的付款地址失效），由 ops 按第 13 节交给 core。

### 10.1 服务端限制（0.10.0，M7 草案第 1.4 节）

每个 HTTP 服务（含 `/healthz`、通道回调入口、反向代理）：

| 项 | 值 |
| --- | --- |
| `ReadHeaderTimeout` | 10 秒 |
| `ReadTimeout` | 30 秒 |
| `WriteTimeout` | 60 秒；导出接口（C4 `/exports/*`、`/statements/export`、`/withdrawals/export`）所在的 core 后台端口 180 秒；反向代理按路由：`/admin/core/` 180 秒，其余 60 秒 |
| `IdleTimeout` | 120 秒（反向代理不小于后端） |
| `MaxHeaderBytes` | 64 KB |
| 请求体上限（服务端 `MaxBytesReader`） | 后台与内部接口 1 MB；站点接口（C1）64 KB；通道回调入口 256 KB（超过时的响应格式按合作商约定，不要求第 4 节结构，0.11.0）；告警（C9）64 KB |

- 超限返回 `INVALID_PARAM`（HTTP 413 时响应体仍按第 4 节结构）。每个服务有"慢体连接在 `ReadTimeout` 后被断开"和"超过上限被拒"的测试。
- 反向代理（`production`、`sandbox`）：TLS 按规范化后的 SNI（小写、去末尾点）选证书，查不到即终止握手；`X-KJ-Host` 按 SNI 写入；`Host` 与 SNI 不一致（忽略端口）或没有 SNI 的连接一律返回 421、不转发；80 端口只做 ACME 验证和跳转，跳转只对证书目录里存在的域名，其余 400。`development` 没有 TLS，`X-KJ-Host` 回退为按 `Host` 写入。代理层请求体上限 2 MB；同一来源并发连接上限和总并发连接上限由 `KJ_PROXY_MAX_CONNS_PER_IP`、`KJ_PROXY_MAX_CONNS` 设置。
- `production` 下反向代理的响应头：总平台域名 `Strict-Transport-Security: max-age=31536000; includeSubDomains`，子平台绑定的域名只 `max-age=31536000`；`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`X-Frame-Options: DENY`；CSP 含 `base-uri 'none'; form-action 'self'; frame-ancestors 'none'`。站点必须按域名（SNI）调用站点接口，IP 直连会被拒绝（无 SNI 时 TLS 握手终止；有 SNI 但 `Host` 不一致时 421，0.11.0）。
- 按域名提供的内容（0.13.0，需求 v3.11 F64）：站点接入文档 `/docs/` 只在子平台绑定的域名上提供，总平台域名（`KJ_ROOT_DOMAIN`）上 `/docs/` 返回 404（反向代理按 SNI/`X-KJ-Host` 判断）。后台的帮助页面内容由 admin-web 在 `/help/` 下提供：服务端核对 `Authorization: Bearer` 里的访问令牌（C7：签名、`exp`、`roles`、`ptype`）后按角色放行文件，无效或缺失一律 401；admin-web 为此只需要 org 的公钥（部署配置 `KJ_ORG_JWKS`，与 usdt-signer 相同的取法）。

## 11. 部署环境与开发开关

每个服务启动时读取以下环境变量，由 ops 的部署配置提供。

| 变量 | 取值 | 说明 |
| --- | --- | --- |
| `KJ_ENV` | `production`、`sandbox`、`development` | 必须设置；没有设置或取值不在这三个之内时，服务拒绝启动 |

## 12. 编号格式

各种编号的格式如下。生成方按此生成，用全局递增序列，不按平台分段、不复用；org 和 core 在数据库里加约束。

| 对象 | 格式 | 示例 | 生成方 |
| --- | --- | --- | --- |
| 平台编号 | `root`，或 `^P[0-9]{2,6}$` | `P01` | org |
| 子平台代号（登录名前缀） | `^[a-z][a-z0-9]{0,15}$`，`root` 保留给总平台 | `a` | 总平台管理员新建子平台时填写 |
| 商户 | `^M[0-9]{2,8}$` | `M01` | org |
| 代理 | `^AG[0-9]{2,8}$` | `AG01` | org |
| 站点 | `^[0-9]{4,12}$` | `1001` | org |
| 账号 | `^U[0-9]{4,10}$` | `U0001` | org |
| 通道账户 | `^CA[0-9]{4,10}$` | `CA0001` | core |
| 资金账户 | `^FA[0-9]{4,10}$` | `FA0001` | core |
| 店铺（0.14.0） | `^SH[0-9]{4,10}$` | `SH0001` | core |
| 店铺码（0.14.0） | `^SC[0-9]{4,10}$` | `SC0001` | core |
| 店铺码分配（0.14.0） | `^AL[0-9]{12,20}$` | `AL202611110000001` | core |
| 预付款充值单（0.14.0，系统外充值与 USDT 充值共用） | `^PT[0-9]{12,20}$` | `PT202611110000001` | core |
| 登录名的名称部分 | `^[a-z0-9][a-z0-9_-]{0,31}$`；商户管理员、代理新建的账号由 org 在前面加"所属编号的小写-"（如 `m01-alice`，登录名为 `a.m01-alice`）；格式只检查填写的部分，加前缀后整个登录名不超过 64 个字符 | `finance01` | 新建账号时填写（0.6.0 起） |
| 代理推广码 | 8 位，大写字母和数字，不含 `0`、`O`、`1`、`I`；M4 之前的预置数据为 6 位，照常有效 | `K7M2Q9WX` | org（0.6.0 起） |

- 告警记录编号（`recordId`）由 ops 生成，是不透明的字符串（最长 64），不按格式预先判断，按编号查不到即"不存在"。
- 格式由程序检查，不写进 OpenAPI 的 `pattern`（写进去会被按契约生成的代码拦成 `INVALID_PARAM`）。
- 收到不符合格式的编号时不查数据库，按"不存在"处理，即返回该接口对"不存在"规定的结果：多数后台接口和内部接口为 `NOT_FOUND`；接口另有规定的按其规定（如 C6 的 `SITE_NOT_FOUND`、`valid = false`），契约没有写"不存在"结果的，与该实现对不存在的编号的处理相同。站点接口的 `X-KJ-Key-Id` 不符合站点编号格式时按验签失败返回 `UNAUTHORIZED`。
- 列表接口的筛选条件不符合格式时返回空列表（第 8 节）。

## 13. 保密文件（0.8.0）

需求 10.1 要求保密内容只留在内存里、服务器磁盘上不出现明文。经环境变量交给容器时 Docker 会把它写进磁盘上的容器配置，所以正式环境和沙箱改用保密文件。

- ops 的启动脚本用该服务对应的 1Password 访问令牌取出**它自己的**保密变量，写成 tmpfs 上的一个文件（`/run/kj-secrets/<服务名>.env`，目录 `0700`、文件 `0400`，属主为该容器的运行用户），**只把这一个文件**只读挂进该服务的容器；服务从 `KJ_SECRETS_FILE` 读取。
- 格式：每行 `名称=值`，值到行尾，不加引号、不转义；`#` 开头的行和空行忽略。以下情形拒绝启动：读不到文件；某行没有 `=`；行尾有 CR；名称重复；名称不在本服务的保密变量清单里（含 `KJ_ENV`、`KJ_DEV_` 开头的和别的服务的变量）；文件里的变量与环境变量同名。
- 读完与环境变量合并后，再做第 11 节的开发开关检查。日志只写读到了哪些名称，不写值。
- `production`、`sandbox` 下：本服务保密变量清单里的变量只能来自文件，出现在环境变量里拒绝启动（日志写明名称）；文件必须在 tmpfs 上、权限不宽于 `0400`，否则拒绝启动。`development` 下两种都可以（本机编排和集成测试照旧用环境变量）。
- 保密变量清单由各服务的设计文档列出，与 ops 的 `deploy.md` 第 2 节的表一致。文件在服务运行期间留在 tmpfs 里，服务重启时可以再读。usdt-signer 的私钥文件流程不变（就绪后由启动脚本删除）。
- 0.10.0 起（第 15 节）：运行中的服务的保密变量清单里**没有** `KJ_DB_OWNER_URL`，它出现在保密文件或环境变量里都按本节规则拒绝启动；`migrate` 子命令的保密变量清单只有 `KJ_DB_OWNER_URL`（`development` 下 core 的 `--dev-seed` 另经环境变量读主密钥）。org 的 `org-admin` 一次性入口和各服务的 `rekey-table`、`rekey-format` 一次性命令同样只在执行时拿到属主连接串。
- 沙箱与正式环境的保密内容完全不同（各自的保险库和访问令牌）。沙箱 org 的令牌签名密钥编号（`kid`）固定以 `sbx-` 开头（`sandbox` 下 org 不用这个前缀拒绝启动）。`production` 下：org 拒绝用这种 `kid` 启动，core、usdt-signer 拒绝这种 `kid` 签发的令牌和审核声明（按验签失败处理）。`sandbox`、`development` 下照常接受（C7 第 3 节）。

## 14. 存活检查（0.8.0）

- 每个 HTTP 服务在内部端口提供 `GET /healthz`（有两个端口的 core、org 两个端口都提供）：不验签；正常时 200，`{"code":"OK","message":"","data":{"service":"<服务名>","version":"<程序版本>"}}`；依赖的数据库不可用时 503，`code` 为 `UNAVAILABLE`。不返回其他内容（不含配置、地址、错误详情）。
- 服务名：`core`、`org`、`channel-aggregator`、`channel-usdt`、`channel-mock`、`usdt-signer`、`ops`（告警转发）、`tron-fake`。
- 程序版本（0.11.0，需求 F63）：发布构建（ops `release/build.sh`）给每个仓库的 `docker build` 传构建参数 `KJ_BUILD_VERSION`（发布版本，如 `2026.10.29-1`）和 `KJ_BUILD_COMMIT`（该仓库提交号的前 12 位，小写十六进制），程序在构建时写死，`/healthz` 的 `version` 为 `<KJ_BUILD_VERSION>+<KJ_BUILD_COMMIT>`。没有传构建参数时（本机开发、集成测试）为 `dev+unknown`，只传了提交号时为 `dev+<提交号>`。不从运行时环境变量读取（部署配置改不了程序报告的版本）。admin-web、docs-site 是静态页面，构建时同样写入，admin-web 显示在"系统版本"页和页面底部，docs-site 显示在页面底部。
- usdt-signer 只在已读入全部配置的钱包私钥、且数据库可用后才返回 200（启动脚本以此为"就绪"再删除私钥文件）。
- 反向代理先规范化路径（解码、合并 `.`、`..` 和重复的斜杠）再判断：规范化前后不一致的路径（路径段为 `.` 或 `..`、含其百分号编码写法、含 `//`、含反斜杠、含编码的斜杠等）一律返回 400 `INVALID_PARAM`、不转发（0.14.6，此前写的是 404；ops 自 T-063 起按 400 实现）；规范化后路径为 `/healthz` 或以 `/healthz` 结尾的外部请求一律返回 404、不转发。
- ops 每分钟检查一次，连续 3 次失败按 C9 发 `critical`（`dedupKey: service-down-<服务名>`），恢复后发一条 `info`。编排的 `healthcheck` 用同一个接口。

## 15. 数据库迁移（0.10.0）

依据 M7 契约草案第 1.1 节（`docs/architecture/m7-contract-draft.md`）、backlog A-01、A-09。适用于有数据库的服务：core、org、channel-usdt、usdt-signer。

- **迁移由一次性容器执行，运行中的服务不持有属主连接串。** 每个服务的程序提供子命令 `migrate`：读 `KJ_DB_OWNER_URL`，执行未执行的迁移文件并授权，然后退出（0 成功、1 失败）。授权需要应用角色名时，`migrate` 可另读非保密变量 `KJ_DB_APP_ROLE`（如 usdt-signer 的 `kj_signer_app`，0.10.2）。编排里对应一次性服务 `<服务名>-migrate`，主服务在它成功完成后才启动；服务一律经 ops 的部署脚本启动，脚本总是先运行 `*-migrate`。
- **`schema_migrations`** 记每个已执行文件的 `version`（文件名）、`sha256`（文件内容）、`applied_at`；应用角色有 `SELECT`。编号比较一律按文件名的数字前缀。
- **主服务启动时的核对**（用应用角色）：(a) 程序内嵌的每个文件都已在表中且 SHA-256 一致，否则拒绝启动（"先运行 migrate"或"迁移文件被改动"）；(b) 表里有、程序里没有的记录：编号大于程序内嵌的最大编号时允许启动（回滚态），日志 warning"数据库领先于程序：<版本列表>"并按 C9 发一次 `warning`（`dedupKey: schema-ahead-<服务名>-<日期>`）；(c) 表里有、程序里没有、编号不大于内嵌最大编号的记录：拒绝启动。
- **`migrate` 的行为**：先核对已执行文件的 SHA-256（不一致退出 1）；再按顺序执行程序有、表里没有的文件；然后对表里多出的高编号记录只记 warning、退出 0。程序有未执行的文件、同时表里又有编号大于内嵌最大编号的记录时退出 1（"数据库版本领先于程序且程序有未执行的文件：疑似分支混用"），不执行任何文件；表里有编号不大于内嵌最大编号的多余记录时退出 1。首次升级到本版时，表里没有 `sha256` 的旧记录以当前文件内容补写一次，日志逐条记。`--dev-seed` 选项只在 `development` 写开发预置数据，其他环境退出 1。
- **必需的测试**（各服务）：改动一个已执行文件的一个字节后 `migrate` 和主服务都拒绝；表里多一条更高编号的记录时主服务能启动、`migrate` 不执行且退出 0；多一条更低编号的记录时两者都拒绝；表里多一条更高编号记录且程序另有一个未执行文件时 `migrate` 退出 1；`--dev-seed` 在非 `development` 退出 1；`production`、`sandbox` 下主服务见到 `KJ_DB_OWNER_URL` 拒绝启动。
- **迁移文件的规则**（细则在开发规范第 5 节）：锁大表或长时间运行的语句单独一个文件，第一行 `-- kj:no-transaction`，不包事务、必须幂等、失败不记录；先扩后收——删除列、改列类型、加 `NOT NULL`、加新约束、加状态值检查，以及任何会拒绝旧程序写入的触发器、检查约束、唯一索引，都要晚一个发布版本；新文件编号必须大于任何已发布版本用过的编号（含已回滚的版本），回滚后的下一个发布必须包含数据库里已执行的全部文件，被回滚版本的迁移不撤销。新数据库角色不在迁移里建，由部署脚本在 `*-migrate` 之前以数据库超级用户执行幂等的角色脚本。
- **org 的属主权限入口**：常驻的高权限连接改为专用角色 `kj_org_rootcred`（`KJ_DB_ROOTCRED_URL`），只能插入授权、设置票、待绑定密钥和总平台账号的登录会话、刷新令牌，不能直接改密码和动态码列；紧急命令中需要属主的（`create-root-account`、超级管理员的 `disable-account`/`enable-account`、`reset-root-mfa`、`rekey-format`）经一次性入口 `org-admin` 运行，其余命令仍在运行中的容器里执行。细则在 org 的设计文档。

## 16. 数据脱敏（0.12.0，需求 10.3"数据脱敏"）

设计与理由见根目录 `docs/architecture/data-masking-draft.md` 第 4 版（三轮安全审查）。各有数据库的服务（core、org、channel-usdt）提供两个子命令，与 `migrate` 一样在一次性容器里运行；编排、通用改写、检查、导出导入由 ops 负责（`kj-mask.sh`、`ops-mask`）。usdt-signer 的库不参与脱敏，不提供这两个子命令。

- **只在脱敏用的库上运行**：`mask-secrets` 和检查子命令启动时先读库里的标记表 `kj_mask_marker`（由 ops 的"只恢复数据库"恢复写入，不属于任何服务的迁移）；没有这张表或其中没有一行，退出码 1，不做任何改动。
- **`<服务> mask-rules`**：不连数据库，向标准输出打印一个 JSON 对象，退出 0。字段（都必需，没有内容时为空数组或空对象）：
  - `service`：服务名。
  - `keepText`：`["<表>.<列>"]`，必须原样保留的文本列（币种、网络名、角色名、通道代号等固定取值）。
  - `keepJsonPaths`：`["<表>.<列>:<JSON 路径>"]`，`jsonb` 里必须原样保留的值（如分账明细的金额、参与方类型）；JSON 路径用 `$.a.b`、数组元素用 `[*]`。值为 JSON 数字或第 2 节金额格式的字符串时，ops 不做"不同取值个数"与字符格式的核对（模式扫描照常，0.12.3）。
  - `maskNumeric`：`["<表>.<列>"]`，要脱敏的整数列（块号、日志序号、Telegram 接收人编号等）。
  - `timeNumeric`：`["<表>.<列>"]`，存时间的整数列；`units`（顶层字段，0.12.1）：`{"<表>.<列>": "seconds" | "steps30"}`，`timeNumeric` 的每一列都要有。
  - `ids`：`[{"column": "<表>.<列>" 或 "<表>.<列>:<JSON 路径>", "entity": "<实体类型>" 或 null, "typeBy": "<表>.<列>" 或 null, "typeMap": {"<typeBy 的值>": "<实体类型>"}}]`；`jsonb` 数组里的编号按同一元素的另一字段区分时，`typeBy` 写成同一列、同一元素的路径（如 `"orders.split_lines:$[*].partyType"`，0.12.1）；实体类型取 `platform`、`account`、`merchant`、`site`、`agent`、`order`、`payment`、`refund`、`withdrawal`、`channelAccount`、`fundAccount`、`settlement`、`party`（0.16.1：按第 12 节的编号格式在 `merchant`、`agent` 中判定，映射与对应实体共用；两种格式都不符合的值按普通文本脱敏。用于同一行没有类型列的提供方编号，如 core 的 `shopcode_rotations.last_provider_id`、`orders.fee_provider_id`，以及 `typeMap` 里 `prepaid` → `party`）、`other:<名称>`；`root` 与契约里固定的系统操作人（`ops-cli`、`system`）一律原样保留，不改写、不登记为原值（0.12.4）。`ids` 的列可以是 `text[]`（逐元素映射，0.12.2）；列里不符合该实体编号格式的值（如 `ops-cli`）按普通文本脱敏，不报错（0.12.2）。
  - `encrypted`：`["<表>.<列>"]`，本服务的全部加密列。
  - `recomputed`（0.12.1）：`["<表>.<列>"]`，由 `mask-secrets` 重写的列：按新的假值重算的派生列（后 4 位、打码、查重摘要、与密文对应的地址等），以及有格式、唯一约束或须与其他列保持对应的标识（如登录名、平台代号、域名，0.12.2）。ops 的通用改写跳过这些列（同 `encrypted`），不做 `keepText` 的取值核对，模式扫描不扫这些列，原值摘要扫描照常（原值不得出现）。生成列（`GENERATED`）不写，列进 `keepText` 时同样不做取值核对。
  - `scope`：`{"<表>": {"kind": "platform", "column": "<列>"} | {"kind": "via", "column": "<列>", "references": "<表>.<列>" 或 "<服务>:<表>.<列>"} | {"kind": "global", "reason": "<一句话>"} | {"kind": "none"}}`，每张表一项。`none` 表示不导出数据（表结构照样导出，导入后为空，0.12.1）。引用别的服务的库时写 `<服务>:<表>.<列>`（如 channel-usdt 按 `core:channel_accounts.id` 筛，ops 先从该服务的库读出授权范围内的编号，0.12.2）。凭据与防重放类表必须为 `none`；汇总了全部子平台的总平台行用 `rowFilters` 排除。
  - `rowFilters`：`[{"name": "<名称>", "table": "<表>", "where": "<只引用本表列的 SQL 条件>", "cascade": ["<表>.<列> → <表>.<列>"], "recompute": "<说明>" 或 null}]`；`name` 为 `usdt-orders` 的条件表示"USDT 订单"，授权不含 USDT 订单时按它删除；`rootAggregates` 表示总平台汇总行，一律删除。`where` 只能引用不会被改写的列（`keepText`、受约束的状态列、未列入 `maskNumeric`/`timeNumeric` 的数字列），例外：整个条件为 `<ids 列> = 'root'`（0.12.4）；ops 在改写之前求值并记下匹配的行（0.12.3）。`cascade` 一律写成"已删除的行 → 要连带删除的行"（`<被删表>.<列> → <连带表>.<列>`，0.12.3 统一）。
  - `resetTables`：`["<表>"]`，导入后清空的待发记录表；名字以 `_outbox` 结尾的表必须在内。
  - 同一列只能出现在 `keepText`、`ids`、`encrypted`、`recomputed` 之一，重叠时 ops 拒绝（0.12.3）。`recomputed` 里长度短于 6 的值由服务随机重生成，ops 的原值摘要对它们不做同列比对（0.12.3）。
  - `checks`：`["<子命令>"]`，脱敏后要运行的一致性检查子命令（core：`mask-check-ledger`；org：`mask-check`；没有则为空）。
- **`<服务> mask-secrets`**：读保密变量 `KJ_DB_MASK_URL`（脱敏库的超级用户连接，只出现在这个子命令和检查子命令的保密变量清单里，服务的其他入口（含 `mask-rules`）出现它即拒绝启动，0.12.1 更正）、`KJ_MASK_MASTER_KEY`（目标环境的主密钥，保密文件）与非保密变量 `KJ_MASK_MASTER_KEY_VERSION`（目标环境主密钥的版本号，不设为 1，0.12.1），不读 `KJ_DB_OWNER_URL` 和正式主密钥。把 `encrypted` 的每一列改为新生成的假值并用 `KJ_MASK_MASTER_KEY` 加密；org 另把全部账号停用、密码与动态码清空，站点接口密钥与通道凭据重新生成（不输出）；core 另把状态为 `waiting` 的等待生效操作改为撤销（0.12.3，导入后不会自动执行）。告警接收人等导入后会对外发送的配置，所在表的 `scope` 为 `none`（0.12.3）。在一个事务里完成；每张表核对受影响行数等于行数，不等则回滚、退出 1。**顺序**：`mask-secrets` 在 ops 的通用改写（含编号映射）之后运行；密文的附加数据含编号，之后任何步骤不得再改编号（0.12.1）。
- **店铺码**（core，0.14.0）：码的内容、原图改为假值（码的内容改成 `https://masked.invalid/<序号>/` 这类不能付款的地址），内容摘要、`digestPrefix`、`contentHost` 列入 `recomputed`；脱敏库导入测试环境后不得出现真实收款码。付款页令牌不入库，测试环境的 `KJ_PAY_TOKEN_KEY` 与正式环境不同即可。
- **启用授权账号**（org，0.12.3）：`org-admin mask-activate <登录名> --password-file <文件>`，只在 `KJ_ENV` 为 `sandbox`、`development` 时可用（`production` 退出 1）：启用该账号、生成随机初始密码写进文件（0400）、置为首次登录必须改密码并绑定动态码；登录名不存在退出 1。ops 的导入在启动后对清单里的每个授权账号运行它。
- **检查子命令**（`checks` 里列出的）：读 `KJ_DB_MASK_URL`，只读，通过退出 0、不通过退出 1 并输出不通过的项（表名、列名、计数，不输出值）。
- **必需的测试**（每个服务，测试名前缀 `TestMask`）：规则里的表、列、JSON 路径都存在；每个加密列都在 `encrypted`；每张表都有 `scope`；`_outbox` 表都在 `resetTables`；凭据与防重放类表为 `none`；每个整数列都在 `maskNumeric`、`timeNumeric` 或本服务的"普通数量"清单里；开发预置数据里符合任何编号格式的文本列都在 `ids` 或"不是编号"清单里；没有标记表时两个子命令退出 1 且不改数据；`mask-secrets` 之后用 `KJ_MASK_MASTER_KEY` 能解密、用原主密钥不能、原值不再出现。

## 17. 面向平台人员的用词（0.13.4，需求 v3.13 第 3.1 节）

子平台的账号（访问令牌 `ptype` 为 `platform`、`merchant`、`agent`）看到的一切文字——接口返回的 `message`、记录里的操作人显示名、发给子平台的告警标题和正文、后台界面、帮助手册、站点接入文档——不出现"子平台"和"总平台"两个词：子平台称"平台"或"本平台"，总平台做的事称"运营方"，系统自动做的称"系统"。返回给总平台账号（`ptype` 为 `root`）的文字不受此限，仍用"总平台""子平台"。契约、设计文档、代码注释、日志等内部材料不受此限。同一段文字两类调用方都可能看到时，按调用方分别给出，或改写成两类都适用的说法（如"收款已暂停"）。

对外公开的材料（站点接入文档及其示例、可下载文件；0.15.3，需求 v3.15 第 3.1 节补充）另外不出现：内部岗位与审批流程（"平台财务""审批""人工补单""人工补发"）、内部状态或流程名（"待认领""冻结期"等，改用面向站点的说法）、多租户结构的描述（"所属平台""所有平台""同一个沙箱""平台已停用"）、里程碑与任务编号、内部项目名（`core`、`org` 等）、本仓库的脚本或路径。页面不渲染源文件开头的"用途/状态/依据"元信息。
