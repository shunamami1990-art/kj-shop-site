## 1. 总原则

1. 设计文档是代码的上游。设计与代码必须一致，粒度到：模块职责、接口定义、数据表结构、核心流程。
2. 文档与代码在同一次提交中更新，不允许"先改代码，以后补文档"。
3. 能从代码、契约和需求机械推导的文档，由 AI 维护；需要人判断的（产品意图、对外措辞、用户手册），AI 起草，人审核。
4. 遇到文档缺失、文档与需求或契约冲突、需求本身不清楚：不要猜测后直接写代码。项目会话写到 `issues/to-architect/` 后停下；根目录会话向负责人提出。

## 3. 各文档的内容要求

### 设计文档（`docs/design.md` 或 `docs/design/<模块>.md`）

- 模块职责与边界；依赖哪些项目或模块、被谁依赖。
- 关键流程的时序图（凡是跨服务的流程都要画）。
- 有状态流转的对象画状态机。
- 错误处理策略。
- 已知限制与待办。
- 核心数据结构可以用类图，但不强制。

### 数据库文档（`docs/database.md`）

- ER 图。
- 每张表：表名、字段、类型、约束、索引、用途；表名、字段名与迁移脚本完全一致。
- 行级安全策略（使用的项目）、数据库角色及各自的权限。

### 接口契约（`contracts/*.yaml`）

- 项目对外提供或调用的每个 HTTP 接口都以契约为准；代码中的路由、参数、返回结构与契约一致。
- 契约由架构师维护；项目需要改接口时写 issue，不得自行改变接口行为。
- 契约下次修订时，错误码改为在 `components` 中统一定义，代码中的错误码枚举与之一致。

### 按契约生成代码（ADR-017）

- 接口的类型、服务端接口（以及需要时的客户端）由工具从项目自己的 `contracts/` 副本生成，不手写，不手改生成的文件。Go 项目用 `oapi-codegen`，前端用 `openapi-typescript`，版本固定在项目的 `go.mod`（`tool` 指令）或 `package.json` 里。
- **代码生成一律在 Docker 容器里运行，不得在宿主机上安装或运行生成工具**（负责人 2026-10-14 出于安全考虑的要求）。
- 生成的代码提交进仓库；契约升版本后重新生成，并与依据版本的更新放在同一次提交里。
- 检查会在副本上重新生成并与提交的代码比较，不一致即失败。
- 例外：`channel-mock` 在 ADR-017 之前已用标准库手写完成，暂不改为生成代码（负责人 2026-10-14 同意），等其他 Go 项目用上生成代码后再由架构师派任务统一改。在此之前它不受本节约束，但契约变化时仍须同步修改并通过契约测试。

### ADR（`docs/architecture/adr/NNN-标题.md`）

固定结构：

- 状态：已接受 / 已被 ADR-NNN 取代 / 部分内容已被 ADR-NNN 修订。
- 背景：要解决什么问题，有什么约束。
- 候选方案：至少两个，各自的优缺点。（ADR-016 之前的记录没有这一节，不补写。）
- 决定：选了哪个，为什么。
- 后果：好处、代价、需要注意的事项。

需要写 ADR 的情形：引入或替换框架、中间件、数据库；改变项目边界；改变通信方式；改变认证授权方案；任何影响超过一个项目的技术选择。

### 部署文档（`ops` 的 `docs/deploy.md`）

各环境的配置差异与环境变量清单、发布步骤、回滚步骤、监控指标与告警、常见故障排查、备份恢复步骤。

## 4. 图表

1. 所有图表用 Mermaid 写在 Markdown 代码块里，不使用图片文件。
2. 图表类型：流程和依赖用 `flowchart`；调用时序用 `sequenceDiagram`；状态流转用 `stateDiagram-v2`；数据库用 `erDiagram`；数据结构需要时用 `classDiagram`。架构分层也用 `flowchart`，不用 C4 图。
3. 必须画图的只有三类：状态机、跨服务的时序、表结构。其余可以不画。
4. 图中节点名称与代码中的服务名、包名、接口路径、表名完全一致。
5. 单张图超过 20 个节点时拆成多张。

## 5. 每次任务的流程

### 动手前

1. 阅读本次任务涉及的设计文档、数据库文档、相关契约；根目录会话还要读相关的 ADR。
2. 检查文档的"依据"版本（第 7 节），落后时按第 7 节处理。
3. 本项目内部的设计（表结构、内部模块、流程）缺失时，先补写设计文档，再写代码；不需要等人确认，由代码审查核对。
4. 会影响契约或其他项目的，写 issue 等待，不要自行决定。
5. 属于"需要写 ADR 的情形"的，由架构师先写 ADR，经负责人确认后再实施。
6. 记录基线（v1.6 改）：上一个任务结束时全量验证已通过，动手前不必再跑一遍全套检查（跑一遍要好几分钟，提交钩子会跑）；只跑与本次改动相关的测试文件，记下当时已经失败的项。总结里把"原来就失败的"和"本次引入的"分开写。开发中也只跑相关的部分，提交前不必手动跑全套。

### 编码中

7. 接口以契约为准；表结构先改 `docs/database.md`，再写迁移脚本。
8. 不引入设计文档中没有声明的依赖、中间件：先在设计文档的"技术约定"里写明依赖和理由，再引入。
9. 任务文件"风险与测试"列出的每一处风险都要有测试：正常情况、反例、边界，修复缺陷时加回归测试。
   - 退避、负缓存、限流、去重窗口的起点，取失败或事件发生那一刻**重新获取**的当前时间，不要用操作开始时取的时间（操作本身可能等到超时才失败，窗口在写入时就已过去）；并写一个"操作耗时超过窗口"的测试（可控时钟在请求过程中推进）。
10. 不得为了让检查通过而放宽断言、跳过或删除测试、改动需求或契约的含义；测试确实错了的，在总结里写明原因。
11. 数据库迁移（v1.3，契约 common.md 第 15 节）：
    - 迁移由 `migrate` 子命令在一次性容器里执行；每个文件一个事务。会锁大表或长时间运行的语句（`CREATE INDEX CONCURRENTLY`、全表重写）单独一个文件，第一行写 `-- kj:no-transaction`，不包事务；这种文件必须幂等（`IF NOT EXISTS`），建索引的第一句 `DROP INDEX CONCURRENTLY IF EXISTS <名>`，失败不记 `schema_migrations`，修复后重跑同一命令。
    - **先扩后收**：删除列、改列类型、加 `NOT NULL`、加新约束、加状态值检查，以及任何会拒绝旧程序写入的触发器、检查约束、唯一索引，必须在"程序已不再依赖旧形态"的下一个发布版本才上；同一个发布里只允许新增表、新增可空列、新增索引、新增行级安全放行、只记录不拒绝的触发器。新列的值不能作为旧程序改过的行的可信状态，需要时用 `updated_at` 或版本列判断。
    - 编号：新迁移文件的编号必须大于任何已发布版本用过的编号（含已回滚的版本）；回滚后的下一个发布必须包含数据库里已执行的全部迁移文件，被回滚版本的迁移不撤销；热修补分支从主干取编号。
    - 迁移不写业务数据的修正，需要时用一次性命令并记录；新数据库角色不在迁移里建（由 ops 的角色脚本以超级用户建）。
12. 新增以属主权限运行的 `security definer` 函数时，必须在设计文档列出函数名、调用方角色、只接受什么参数和为什么需要它（v1.3）。
13. 分支（v1.4）：项目会话只在 `main` 上提交；`production` 分支只由架构师在全量验证合格后把 `main` 原样快进过去，项目会话不得切换、提交或合并 `production`。发布包只从 `production` 构建。

### 提交前自检

11. 列出本次改动涉及的文档，逐项确认已更新：

| 改动 | 必须更新 |
| --- | --- |
| 实现或修改了契约中的接口 | 对应的设计文档 |
| 表结构变更 | `docs/database.md` |
| 模块职责或依赖变化 | 设计文档；跨项目的由架构师更新 `architecture.md` |
| 引入新依赖或技术选型变化 | 设计文档的"技术约定"；跨项目的由架构师写 ADR |
| 新增环境变量或部署步骤 | 本项目的设计文档；`ops` 同步更新 `docs/deploy.md`；跨项目的由架构师更新 `skeleton-seed.md` |
| 页面或交互变化（阶段 4 起） | `admin-web` 的 `docs/ui/design-system.md` |

12. 纯重构、不改变外部行为的修复、日志、注释、格式，不需要更新文档；在总结中写明"本次改动无需更新文档"。

### 任务总结格式

- 改了哪些代码文件。
- 更新了哪些文档，或声明无需更新。
- 检查和测试的结果（只写可验证的事实，如"契约测试 12/12 通过"），写明运行的命令；与开始前的基线对比。
- 未验证的内容：没有测试覆盖、或受环境限制没能验证的部分。
- 需要人工确认的事项：未决问题、提交的 issue、待审核的内容。

## 6. 文档写作约定

- 使用中文，技术名词保留英文原文。
- 文件名用小写英文、数字和连字符；模块名与代码目录名一致。
- 每份文档开头写明：用途（一句话）、状态（含本文件的版本号，如有）、依据（所依据的上游文档及其版本，见第 7 节）。不写"最后更新日期"，以 git 记录为准。
- 废弃的内容直接删除，历史通过 git 查看。例外：ADR 一旦接受不再修改，被取代时只在状态里注明。

## 7. 版本号与"依据"

### 什么是版本号

版本号是写在文档开头"状态"一行里的编号，用来标识这份文档内容的一个确定版本。它不是 git 标签，也不是阶段编号。

| 文档 | 版本号的形式 | 记录在哪里 | 谁更新 | 什么时候升 |
| --- | --- | --- | --- | --- |
| 需求 `requirements.md` | `v3.3` | 文件开头的"状态"行和变更说明 | 架构师，经负责人确认后 | 每次经确认的修改升第二位；整体重写升第一位 |
| 总体架构 `architecture.md` | `v2.0` | 文件开头的"状态"行 | 架构师，经负责人批准后 | 同上 |
| 契约 | `0.2.1` | `contracts/distribution.json` 的 `contractsVersion`，以及 `contracts/README.md` 的变更记录；分发到各项目后在 `contracts/MANIFEST.json` 的 `version` | 架构师 | 按 `contracts/README.md` 的版本规则 |
| 本规范 | `v1.0` | 文件开头的"状态"行 | 架构师，经负责人确认后 | 每次修改 |
| ADR | 不用版本号，用编号 | — | — | 不修改，只取代 |

项目自己的设计文档、数据库文档不设版本号，以 git 记录为准。

### 什么是"依据"

下游文档在开头的"依据"一行写明它是按哪些上游文档的哪个版本写的，例如"依据：需求文档 v3.3、总体架构 v2.0、契约 v0.2.1"。上游文档升版本时，下游文档要复查，复查后把"依据"改为新版本。

| 下游文档 | 依据写什么 | 谁负责复查和改"依据" |
| --- | --- | --- |
| 总体架构、ADR | 需求的版本 | 架构师 |
| 各项目的设计文档、数据库文档 | 契约的版本（项目会话看不到需求和架构，只核对契约） | 初稿由架构师；之后由项目会话 |
| 各项目的规则文件 `CLAUDE.md` | 不写依据；内容变化由架构师直接改 | 架构师 |

### 版本落后时怎么办

**项目会话**，每次动手前：

1. 比较 `contracts/MANIFEST.json` 里的 `version` 与自己设计文档"依据"里的契约版本。
2. 一致：照常工作。
3. 不一致：说明契约在设计文档写成之后改过。
   - 读 `contracts/README.md` 的变更记录，找出从旧版本到新版本之间与本项目有关的变化。
   - 先按新契约更新设计文档、数据库文档和已有代码中受影响的部分，再做本次任务；改完后把"依据"改为新版本，在任务总结里写明"依据从 A 升到 B，更新了哪些部分"。
   - 无法判断新契约对本项目的影响时，写 `issues/to-architect/` 后停下。
4. 不得因为设计文档是旧的，就按旧设计继续写代码。

**架构师**：

1. 改了需求或架构后，复查依据它们的 ADR、架构和契约，需要改的一起改，再把"依据"更新。
2. 改了契约后，复查各项目的设计文档初稿；项目会话已经接手的设计文档不由架构师改，而是在分发后通过 `issues/inbox/` 告知该项目"契约已升到某版本，受影响的是哪几处"。
3. 发现任何文档的"依据"落后于当前版本而没有人处理时，在给负责人的报告里列出。

### 契约的发布节奏与发布清单（v1.3）

- 纯文字澄清（不改接口形状、不改行为）攒到下一次接口变更一起发，期间记在 `docs/architecture/contract-notes.md`；分发脚本会在契约副本变化时于容器里按新契约重新生成代码并与副本一起提交（`distribution.json` 的 `regen`），项目会话只处理生成结果以外的改动。
- 发布清单 `releases/<版本>.json`（ops 仓库，由 `release/build.sh`、`pack.sh` 产出，架构师离线保管的 Ed25519 私钥签名为 `.sig`）字段：`version`、`date`、`contractsVersion`、`repos`（9 个仓库名 → 提交号）、`images`（服务名 → `{ id, archiveSha256 }`）、`baseImages`（镜像名 → digest）、`migrations`（服务名 → 本版新增的迁移文件名 → SHA-256）、`roleScripts`（文件名 → SHA-256）、`audit`（`govulncheck`、`npm audit` 的结果摘要）、`rollbackNeedsRestore`（v1.5，必需：升级到本版本后回滚到更早版本需要同时恢复数据库时为 `true`；`manifest.sh` 生成 `false`，架构师人工复查时按需改为 `true`，跳过的中间版本里有 `true` 时后面的版本也标 `true`）。服务器加载发布包前验签并核对每个归档的 SHA-256，启动前再核对镜像 ID（契约草案 M7 第 1.14 节）。

**其他根目录会话**（集成测试、协调者）：发现自己依据的需求或契约版本落后时，先按新版本更新自己的产出；无法判断时向负责人报告。

## 8. 自动检查

各项目的检查：

- 每个项目的 `.githooks/` 由架构师分发，只读：`run-verify.sh` 在容器里运行全部检查，基础检查写在 `verify-base.sh`（Go 项目：格式、`go vet`、全部测试（`distribution.json` 中 `race` 为 true 的项目带 `-race`，v1.3，core、org）、必需的测试；前端项目：`npm ci`、`lint`、`typecheck`、`test`）。项目根目录的 `verify.sh` 只放额外的检查，基础检查跑完后执行。
- 有数据库的项目（`contracts/distribution.json` 中 `database` 为 true）检查时附带一个临时的 PostgreSQL，测试通过 `KJ_TEST_DB_URL` 连接。
- 必需的测试：`distribution.json` 中每个项目的 `requiredTests`，名字以这些前缀开头的测试必须存在并且通过。例如 `TestSplitCases`（分账用例）、`TestSignatureCases`（签名用例）、`TestTokenCases`（令牌和审核声明用例）、`TestIsolation`（平台隔离）。里程碑验收中写明"由项目自己的测试证明"的测试，也逐个列入 `requiredTests`。必需的测试中有任何一项（含子测试）被跳过即为失败。
- 还没有代码的项目，检查结果为"未开始"，不算"通过"。
- 每次提交前由 git 钩子运行；只包含契约分发的提交只核对契约。

全量验证（`node scripts/verify-all.mjs`，可以只验证指定项目，`--json` 输出机器可读的结果）：

- 契约副本与正本一致。
- 提交前检查已启用、可执行，`.githooks/` 的内容与分发的逐字一致、没有多余的文件。
- `distribution.json` 中 `requiredDocs` 列出的文档存在；设计文档"依据"里的契约版本落后于当前版本时，作为提示列出（不算失败）。
- 各项目的检查结果。
- 每个契约接口都标注了数据范围。
- 路径检查钩子的回归测试（`scripts/guard-paths.test.mjs`）通过。
- 阶段 3 起运行集成测试。

"文档内容与代码一致"无法完全自动检查，由代码审查角色负责核对。

## 9. 与通用版的差异

| 通用版的规定 | 本项目的做法 | 原因 |
| --- | --- | --- |
| 一个 `docs/` 目录放全部文档 | 按第 2 节分散在根目录和各项目 | 多仓库，项目会话看不到根目录 |
| 一个 `openapi.yaml` | 按契约拆分，分发到各项目 | 每个项目只应看到和自己有关的契约 |
| 每个模块一份设计文件 | 只有 `core` 按模块拆分 | 小项目拆成多个小文件反而难读 |
| 文档缺失时先补写，经确认后再写代码 | 项目内部的设计补写后不必等人确认，由代码审查核对；影响契约或其他项目的才等待 | 每份设计都等负责人确认，会让负责人成为瓶颈 |
| 遇到问题当面提问 | 写 issue 后停下 | 项目会话可能无人值守地运行 |
| 废弃内容一律删除 | ADR 除外 | ADR 的价值在于保留当时的决定和理由 |
| 每个文档开头写最后更新日期 | **不采用**，改为写用途、状态和依据 | 日期常被忘记更新，反而误导；以 git 记录为准 |
| `docs/ui/figma.md` | **不采用** | 本项目没有设计稿 |
| C4 架构图 | **不采用**，用 flowchart | Mermaid 的 C4 图还不稳定 |
| 现在就建 `docs/user-manual/` | **不采用**，阶段 4 再建，届时照通用版标注 `[待审核]` | 骨架阶段没有用户可见的功能 |
| 所有类和数据结构都画类图 | 只强制状态机、跨服务时序、表结构三类图 | 画图的工作量和消耗都不小 |
| 错误码统一在 `components` 中定义 | 下次修订契约时改 | 现在改要再升一次契约版本 |
